CISA Domain 4.8: IT Change, Configuration and Patch Management

CISA Domain 4.8: controlled changes, configuration baselines and drift, detecting unauthorized changes, emergency changes, patch management, release management and IS operations reviews.

Muhammad Aamir · 28 November 2026

The change register shows every production change as approved. Can you conclude that no unauthorized change took place? No. This lesson covers CISA Domain 4, Section 4.8: how an IS auditor tests that IT changes, configurations and patches are authorized, implemented as approved and verified in production.

4.8 Controlled change

Change management evaluates and authorizes modifications so the enterprise receives the intended benefit without unacceptable disruption or control loss. It covers code, infrastructure, configurations, schedules, databases, interfaces and security rules. Automation changes how controls operate, not whether they are needed.

A change record includes the request, purpose, affected items, risk, impact, tests, approvals, schedule, communication and fallback. The deployed result is verified and the record closed with evidence. Assess dependencies and segregate incompatible responsibilities. Approval authority follows governance and risk; it is not universally a single job title.

Configuration management

Configuration management identifies items and relationships, maintains approved baselines, tracks status and verifies actual configurations. Detect drift through comparison and investigation. A CMDB containing an old baseline is not proof that production matches it.

Detecting unauthorized production changes

To test whether changes escaped authorization, start with independent evidence of actual changes and trace back to approved records. Good sources are deployment records, configuration comparisons, system logs and artifact histories. Starting only with the change register can miss changes omitted from it. Also test approved changes forward to verify proper implementation, and assess the reliability and completeness of the actual-change population.

Emergency changes

An emergency process expedites necessary action under defined authority.

  • Obtain emergency authorization before implementation where feasible.
  • Retain a minimum record and activity evidence.
  • Test proportionately.
  • Complete formal documentation and independent review promptly afterward.

A genuine emergency may require exceptional action under delegated authority, but retrospective approval is not a standing license for uncontrolled changes.

4.8.2 Patch management

A patch is a software update that corrects defects, including security weaknesses. Patch management controls how updates are assessed, tested, authorized, installed and verified, and it is part of the wider change process. A patch being available does not prove the correct assets have received it.

Inventory affected assets, monitor vulnerabilities and patches, assess exposure and compatibility, prioritize by risk, test appropriately, obtain authorization, deploy, and verify installation and service health. Track failures, exceptions and compensating controls. A tool's "deployed" label may not mean installation or a required reboot succeeded.

Balance the risk of delay with the risk of implementation. A critical actively exploited weakness may justify expedited action under the approved process. Record the decision and verify the result; neither "always wait" nor "install everything immediately" is a reliable universal rule.

4.8.3 Release management

A release packages compatible authorized changes. Plan content, dependencies, resources, testing, support readiness, communications, deployment and rollback. Major, minor and emergency releases can have different approval paths, but deployed artifacts must still be identifiable and controlled. Preserve source and object relationships and protect production libraries.

4.8.4 IS operations and reviews

Operations follows current runbooks for monitoring, jobs, backup, incident handling and escalation. Control operator privileges, manual interventions and handovers. Check that procedures reflect actual services and that exceptions lead to action. Trace a sample of failed jobs, privileged activities and operational alerts through approval, resolution and reconciliation.

Auditor perspective: verify the state after a patch and rollback

The change ticket shows a patch was installed. A later rollback returned one production instance to the vulnerable version, while the inventory retained the patch status. Compare the approved change, deployment events and current versions of all relevant instances. Verify how rollback updates the records and reopens exposure for remediation or authorized acceptance, and examine the temporary safeguards and the deadline for reapplying the patch. A successful installation message is insufficient without verifying the intended version, service behavior, exceptions and updated configuration records.

Practice questions

1. An IS auditor wants to determine whether unauthorized changes were made to production. Which approach is BEST? Answer: trace changes in production deployment logs back to approved records. Starting from the register misses unregistered changes.

2. An emergency change was applied directly to production to stop an outage. What should the IS auditor verify MOST closely? Answer: that documentation and independent review followed promptly afterward. Retrospective approval is not a standing license.

3. A patch tool reports a critical patch deployed to all servers. How can the auditor BEST confirm it is effective? Answer: verify installed versions and service behavior on the affected systems directly. A "deployed" label may hide a failed install or reboot.
