CISA Domain 3.5: System Readiness and Implementation Testing

CISA Domain 3.5: test levels and types, test methods, acceptance ownership, data integrity and application testing, implementation planning and CI/CD pipeline evidence.

Muhammad Aamir · 28 November 2026

Every normal payroll change passes testing, but no test tries an unauthorized pay increase through the bulk import interface. Is the system ready? On the CISA exam, not yet. This lesson covers CISA Domain 3, Section 3.5: system readiness and implementation testing.

3.5 Readiness is evidence

Software testing evaluates software against defined requirements or expected behavior. A useful test states what is checked, the expected result and what the actual evidence shows. Readiness also needs evidence about controls, data, people and support. A high pass rate is weak reassurance when critical requirements or failure scenarios were never included.

3.5.1 Test levels and types

Level What is examined
Unit An individual module, including logic and boundaries
Integration Interactions between components, including interface errors
System The complete integrated solution against system requirements
Acceptance Suitability against agreed business and technical criteria

Levels describe scope; types describe objectives. Performance measures response and throughput; load covers expected and peak workloads; volume covers large data populations; stress goes beyond capacity and tests failure and recovery; recovery proves restoration against objectives; regression checks that changes have not damaged previous behavior; sociability verifies operation beside other systems; compatibility checks platforms, versions and connections.

3.5.2 Software testing

A test strategy connects risks and requirements to cases, environments, data, expected results and release criteria, including normal, boundary, invalid, unauthorized and failure cases. Remaining defects can be accepted only by the right authority with a documented risk decision.

  • White box uses internal code knowledge; black box tests observable behavior against requirements.
  • Top-down integration uses stubs; bottom-up uses drivers.
  • Alpha is a controlled developer or supplier setting, beta uses selected intended users, a pilot limits initial real use, and parallel testing compares old and new (the old system may also contain defects).
  • QA concerns the process; QC examines outputs. Authorized business representatives own business acceptance; a supplier demonstration or developer sign-off is not UAT.

3.5.3 and 3.5.4 Data integrity and application testing

Compare detail as well as totals; aggregates can hide wrong allocations. ACID: atomicity (commit together or not at all), consistency, isolation and durability. ACID support does not prove business rules are correct, and external actions may sit outside the transaction.

Audit techniques include test data, an integrated test facility (fictitious entities in live processing, with safeguards against contaminating results), parallel simulation (auditor-controlled logic on actual data), code review and reperformance. Confirm the tested artifacts match the live version. Use synthetic or masked data; production personal data is not automatically allowed in testing.

3.5.5 Implementation

Readiness includes accepted functionality, working controls, reconciled data, infrastructure, trained users and support. Plan sequence, owners, go/no-go criteria and authority, rehearse critical steps, agree fallback triggers and the latest safe decision point, and verify monitoring, runbooks, service desk support and handover.

Continuous integration merges often and runs automated tests; continuous delivery keeps a tested release ready (the decision may be manual); continuous deployment deploys passing changes automatically. A developer who can alter the pipeline rule and release an unreviewed change may bypass the control. Trace a release from commit and approved merge through build and test results to the exact deployed artifact.

Auditor perspective

Include negative cases: rejected unauthorized activity, invalid input, failed dependencies, duplicate requests and emergency paths. If acceptance proved approved orders reach billing but nothing shows an unapproved order is rejected through an alternate interface, add a safe negative case before recommending readiness. Verify accepted and proposed versions match. Business owners approve acceptance; audit evaluates whether the evidence supports it.

Practice questions

1. Unit testing of the modules of a new system is complete. Which testing should be performed NEXT in the standard sequence? Answer: integration testing of the modules through their interfaces. System and acceptance testing come later.

2. Every normal payroll change passes testing, but no test attempts an unauthorized pay increase through the bulk-import interface. What should the IS auditor recommend? Answer: add misuse cases and test that the control is actually enforced. A pass percentage cannot cover a case that was never tested.

3. A new treasury application passed isolated load and system testing and will share servers with the ledger and payment gateway. Which omitted test is the GREATEST concern? Answer: sociability testing alongside the ledger and payment gateway. The untested exposure is interaction with critical shared systems.
