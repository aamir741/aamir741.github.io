CISA Domain 3.4: Control Identification and Design

CISA Domain 3.4: designing controls early, input checks, batch totals, processing and file integrity controls, output controls and CMMI maturity.

Muhammad Aamir · 28 November 2026

A payroll approver can approve a change, then edit its amount before release. A second approver is added. Is the risk covered? On the CISA exam, no. This lesson covers CISA Domain 3, Section 3.4: control identification and design.

3.4 Designing controls

Design controls around the business risks while requirements and design are developed. Specify the objective, owner, action, evidence and exception handling. Adding controls just before go-live is often costly and incomplete. Trace controls through input, processing and output, including interfaces and privileged access.

Application controls protect the authorization, completeness, accuracy and validity of transactions, and may be automated, manual or combined. General IT controls support them: an automated approval rule is unreliable if unauthorized users can change it in production.

3.4.1 Input controls

Input controls apply at every entry path: screens, files, interfaces, scanners and APIs. Confirm authorized origin, required approval and acceptable data, and separate creation, approval and sensitive master data maintenance.

Check Meaning
Completeness Required information present; presence does not prove correctness
Format Expected character pattern
Validity Value belongs to an allowed set or exists in a reference file
Range and limit Between two bounds, or within a single boundary
Reasonableness Makes sense in its business context
Sequence Expected numbering; investigate gaps
Duplicate Repeated records detected
Check digit Detects identifier entry errors; does not prove ownership
Key verification Independent re-entry

A valid supplier and a correctly formatted bank account do not prove a bank account change was authorized.

Batch controls, errors and processing

Control total Limitation
Record count Equal counts can conceal an omission replaced by a duplicate
Financial total Offsetting differences leave it unchanged
Hash total Sum of a nonfinancial field; not a cryptographic hash
Run-to-run totals Compare between stages, allowing authorized differences

Example: of 100 invoices totaling $50,000, 98 totaling $49,500 post and two totaling $500 are rejected. Reconciliation must include both outcomes, and the rejected items need authorized correction, revalidation and controlled resubmission. Never force agreement with unsupported balancing entries.

Rejected transactions need owners, reasons, aging and resolution; preserve the original data, restrict suspense-file changes and prevent duplicate resubmission. Processing controls include reconciliation, idempotency (a repeat does not repeat the effect), concurrency control, checkpoint and restart, reasonableness and limit checks, and an audit trail.

Files and integrity

Referential integrity keeps relationships valid but does not establish that every value is true. Parity, checksums and CRC detect accidental corruption but do not authenticate against deliberate change. With even parity, data 1011 has three 1s, so the parity bit is 1; simple parity can miss an even number of bit changes. An unkeyed hash does not authenticate origin, because an attacker may replace both message and digest. Digital signatures and MACs provide source authentication under their key and trust arrangements.

3.4.2 Output controls

Reconcile totals before release, restrict distribution, make exceptions visible, protect confidentiality (display, printing, stored exports), apply retention and secure disposal, and require timely review by someone who understands the business. Temporary exports and print queues can expose data even when the application is secure.

Auditor perspective

A requirement to make the system secure is untestable; trace each risk to a specific rule, role and evidence. If an approver can edit after approval, a second approval feature does not address the risk: require invalidation or renewed approval and test bypass routes such as imports and APIs. Link the approver to the version actually released.

CMMI maturity levels: 0 Incomplete, 1 Initial, 2 Managed, 3 Defined, 4 Quantitatively Managed, 5 Optimizing. Verify the model version, scope and evidence; a rating is not certification that every application is secure.

Practice questions

1. A payroll transfer was posted to the wrong employee because two digits of the ID were transposed, and the number belonged to another valid employee. Which control would have BEST prevented this? Answer: a check digit algorithm applied when the ID is keyed. A hash total is detective, and a validity check would pass because the wrong ID is valid.

2. A payroll approver can approve a change and then edit its amount before release. Which control BEST addresses this risk? Answer: invalidate the approval, or require renewed approval, when a material field changes after approval. A second approver or a log does not stop post-approval edits.

3. Of 100 invoices totaling $50,000, 98 totaling $49,500 post and 2 totaling $500 are rejected. What should the IS auditor expect from a sound reconciliation? Answer: both outcomes accounted for, with rejected items corrected and resubmitted under control. Forced balancing entries and equal counts can hide errors.
