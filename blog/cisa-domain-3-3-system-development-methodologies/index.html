CISA Domain 3.3: System Development Methodologies

CISA Domain 3.3: system and architecture types, SDLC models and phases, requirements, development methods, acquisition and the software supply chain.

Muhammad Aamir · 28 November 2026

A team ships weekly with agile and a pipeline, and nobody can show which approved source produced the live release. Is speed a control? On the CISA exam, no. This lesson covers CISA Domain 3, Section 3.3: system development methodologies.

3.3 Whatever the method, accountability stays

A development methodology organizes how needs become an operational system. Whatever the method, the enterprise needs requirements, design, control, verification, acceptance and change evidence. Buying a package or using cloud services changes the delivery work but not accountability for the result.

Business application and system types

System Audit focus
MIS Routine structured reports: definitions, completeness, accuracy, timeliness
DSS What-if models for semi-structured decisions: validate assumptions, inputs and limits
EIS Executive indicators and trends: provenance and definitions
Expert system Rule-based knowledge: rule accuracy, updates, ownership
API Authentication, authorization, validation, versioning, rate controls
Data warehouse and ETL Controlled mapping, reconciliation, lineage, timely loads
ERP Configuration, segregation of duties, master data, interfaces, migration

AI is the broader field, machine learning learns patterns from data; assess data quality, bias, performance, explainability and oversight. SOA and microservices are related, not identical.

3.3.2 and 3.3.3 SDLC models and phases

Waterfall is mainly sequential; iterative development refines through cycles; incremental delivers portions; a project can be both. The V-model links specification to verification, so plan tests while defining requirements.

Phase Purpose
Feasibility Viability, options, supported business case
Requirements definition Business, functional, data, control and nonfunctional requirements with measurable acceptance criteria
Selection or design Package fit and terms, or architecture, data, interfaces and controls
Configuration or development Controlled code, parameters, reviews, unit tests
Final testing and implementation Readiness, acceptance, conversion, authorized deployment
Postimplementation review Live result, control effectiveness, costs, benefits

Define acceptance criteria as requirements develop. A functional requirement states what the system must do; a nonfunctional requirement states a quality or constraint. A requirements traceability matrix links requirements to design, build, tests and acceptance, in both directions. User involvement matters because a perfect specification can still describe the wrong process.

Data modeling: an ERD models entities, keys and relationships; first normal form has atomic values, second removes partial dependency, third removes transitive dependency. Denormalization adds redundancy deliberately and needs controls. An ORM does not guarantee freedom from injection.

3.3.5 Development methods

Prototyping (disposable versus evolving), RAD, agile, object-oriented, component-based, web, DevOps and DevSecOps each need disciplined ownership and evidence. Encapsulation, inheritance and polymorphism do not prove secure implementation. In Scrum the Product Owner orders the backlog, Developers create the increment and the Definition of Done makes quality explicit. Continuous integration, delivery and deployment make controls repeatable, and errors repeatable too. CASE tools, code generators and 4GLs still need testing and protected generation rules.

3.3.7 to 3.3.9 Acquisition

  • An RFI explores the market, an RFP asks for proposed solutions, an RFQ seeks price for specified items.
  • Set evaluation criteria and weights before scoring and assess mandatory requirements separately; a high average cannot hide a failed control.
  • Use scripted demonstrations or a conference-room pilot; a proof of concept is not full acceptance.
  • Configuration changes supported parameters; customization changes program logic and raises upgrade and support complexity.
  • Source code escrow helps only if deposits are complete, current and rebuildable.

Software supply chain

SAST examines code without running it, DAST exercises the running application, composition analysis examines third-party components, and an SBOM lists components and versions. None is a security certificate. A valid signature alone does not establish a trustworthy build: trace one production artifact back to approved source, dependency set, build records, tests and deployment decision, and look for bypassable gates.

Auditor perspective

Check review points, user involvement, traceability and auditability early. Audit advises but does not own the design, write production code or sign business acceptance. EVM and CPM support monitoring; they are not SDLC methodologies.

Practice questions

1. Users dispute whether a delivered system meets their needs because no measurable criteria were ever agreed. When should acceptance criteria FIRST have been defined? Answer: alongside each requirement during requirements definition. Criteria set late let the build define what is correct.

2. A bank licenses a core application from a small vendor. Which contract provision BEST protects the bank's ability to maintain the software if the vendor fails? Answer: source code escrow with verified, complete and current deposits. Audit rights, credits and bonds do not keep the software maintainable.

3. A software bill of materials lists the approved components, but a maintenance pipeline can rebuild and publish artifacts. What is the BEST evidence that a released artifact is trustworthy? Answer: tracing the artifact to approved source, dependencies, build records and the deployment decision. A signature, an inventory or a scan alone does not prove the release path.
